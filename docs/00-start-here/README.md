# 学习入口

## 你的最终目标

完成项目以后，你应该能够独立解释和完成：

- 为什么企业需要这个系统。
- 如何把业务需求拆成可开发的任务。
- 如何设计数据库、API、权限和错误处理。
- 如何用 C#/.NET 和 React 实现端到端功能。
- 如何编写单元、集成和端到端测试。
- 如何使用 Git 分支、Commit、Pull Request 和 Release。
- 如何通过 GitHub Actions 自动检查和部署。
- 如何处理备份、监控、生产故障和版本升级。

## 正确学习顺序

1. 阅读[学习方法](learning-method.md)。
2. 检查[本地环境](environment-checklist.md)。
3. 执行[从零到生产部署路线](roadmap-zero-to-production.md)。
4. 遇到术语时查询[专有名词词典](glossary.md)。
5. 每完成一个阶段，更新项目文档并提交 Git。

## 培训规则

### 规则一：先讲业务，再写代码

任何功能开始前必须能回答：

1. 谁使用它？
2. 用户为什么需要它？
3. 成功结果是什么？
4. 哪些情况必须拒绝？
5. 需要查询或修改哪些数据？
6. 谁拥有操作权限？
7. 失败时前端如何提示？
8. 如何证明功能正确？

### 规则二：一次完成一个垂直切片

不要先写完所有数据库，再写所有后端，最后才写前端。一个垂直切片应该完整包含：

```text
User Story
  → 数据库
  → Domain规则
  → Application用例
  → API
  → React页面
  → 错误处理
  → 自动化测试
  → Git提交
```

### 规则三：后端是业务规则的最终权威

前端验证用于改善体验，不能代替后端验证。用户可以绕过页面直接调用 API，因此权限、库存、金额、状态和并发规则必须由后端重新检查。

### 规则四：不会就查，不能猜

遇到业务规则不清楚时记录问题并向业务负责人确认；遇到技术问题先阅读错误、日志和官方文档。不要通过复制随机代码“碰运气”。

### 规则五：每个阶段必须留下证据

证据包括文档、代码、Migration、测试、Pull Request、Release、部署记录和监控截图。企业项目不能只依赖某个人的记忆。

## 每日学习循环

建议每次学习 60～120 分钟：

1. 复习上一次的业务目标。
2. 只选择一个小任务。
3. 写出验收条件。
4. 实现最小可验证结果。
5. 运行测试。
6. 阅读 Git diff。
7. 提交 Git。
8. 用自己的语言写三句话总结。

如果不能解释刚写的代码，就不算掌握。
